# 图片预算守卫

在图片进入上下文之前把过大的图降采样；请求或摘要溢出时按字节从大到小把图片从表层淘汰。

## 问题

`read_image` 把图片以 data URL（base64）写进消息，上游按文本计 token，实测约 `0.911 token/字节`。一张 538 KB 的 1790×1258 拼图就是约 490,000 token。

而 token 计量器对 `image` 块只按附件引用 JSON 计价（约 45 token），因为第三方网关线路不声明 `imageRequestPricing`。两个数字相差四个数量级，后果是一条死链：

1. 压力读数低于阈值 → 自动压缩不触发；
2. 上游以"内容太长"拒绝请求；
3. 摘要请求把同一批图重新发一遍 → 摘要自己也超窗 → 手动 `/compact` 永远失败。

压缩只保留最新节点，而图就在最新节点里，所以**压缩在结构上永远删不掉它们**。必须从源头守住。

## 用法

安装后无需操作。需要看细节时：

- 不要重读原图。插件已经把超预算的图换成降采样副本，版面与标题可辨；要逐字核对请裁剪局部再读。
- 整页拼图建议交子代理读，主会话只收文字结论。
- 需要更严格或更宽松的预算时，改插件配置里的 `maxImageBytes`（默认 60000 字节）。

## 限制

- 「超预算的图不进入上下文」是硬保证：没有任何可用图片后端时，插件会拦下图片并给出替代命令，而不是放行。
- 救援会在摘要或请求溢出时淘汰最大的图片；淘汰后仍溢出说明原因不在图片，插件不再重试。
- 图像压缩质量由逐级降采样决定，不保证与原图逐像素一致。
